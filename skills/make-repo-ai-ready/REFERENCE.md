# Lessons learned

Files a finished reference build typically has (look for them in `REFERENCE_REPO`, see SKILL.md): `AGENTS.md`,
`CONTEXT.md`, `docs/agent-workflow.md`, `docs/writing-tests.md`, `docs/ci-jobs.md`, `docs/markers.md`,
`docs/fixtures.md`, `<AGENT_SKILLS_DIR>/write-tests-from-plan/`, structural tests for agent files, fixture docs,
marker docs, env docs and repo hygiene, and a PR/MR template.

## Must exist in the docs (propose any that is missing in phase 2)
Each item was a real failure in a pilot or experiment. The rule goes in the docs; the skill only links to it.
1. **Test-case lookup, silent helpers, check the helper against the product, prove setup**: see
   [references/test-management-and-helpers.md](references/test-management-and-helpers.md). Example stale-body case: a setup helper
   returned normally on a 400. Sources for the real body: the product's controller/DTO, or a captured request
   without auth headers.
2. **Beta run command** that prints no credentials: the venv's python, the env flag, and `--no-showlocals`
   if `pytest.ini` has `-l` (better: drop `-l` from `addopts`; it prints fixture logins into CI logs).
3. **Exact assertions over membership**: e.g. an event's action set asserted exactly, with a pointer to a
   correct sibling test (check the pointer: the first one pointed at the wrong test).
4. **Teardown restores only what the test created/changed**, and fails on a pre-existing conflict
   instead of deleting other data.
5. **Declared files include generated docs** (markers/fixtures docs regenerated by the gate).
6. **Simulated activity over real logins/VPN** where the repo has a helper for it.
7. **API over direct DB reads** for assertions.

## Must exist in the skill (steps; the template already has them)
- Triage: search the helper API docs before calling a step UI-only; UI-only steps listed, never dropped.
- An expectation derived rather than copied is marked "inferred" in the ticket and the report.
- One ask covering every question: scope, product source, beta run.
- A change the user dictates counts as approval of that change; any other change is shown again.
- A revision after a failed beta run is a new commit; a second beta run needs the user's yes.
- Fallbacks when `/implement` or `/review` is missing; the review fallback names doc sections to check.
- The PR/MR text is written to `.scratch/<feature>/mr-description.md` and shown in the report.

## Pitfalls while building
- Reviewer files were written for another repo: some rules don't fit (type hints, helper paths, branch naming).
  Show the evidence count and let the user decide per rule.
- After a rebase onto a moved base branch, re-run the overlap check: the base may now hold the same lines.
- Worktrees with a symlinked shared `.venv` import the main checkout's editable package; run the gate with
  `PYTHONPATH=$PWD/src` in the worktree, and never `pip install -e` from the worktree.
- macOS has no `timeout`; don't prefix the beta command with it.
- Eval cost: record the orchestrator's cost too, or the comparison with a baseline is meaningless.
- Generators read the wrong tree in a worktree for the same editable-install reason; set `PYTHONPATH=$PWD/src`
  before `--write` too.
- Hand-written CI facts were wrong twice until a second agent checked them against the YAML.
- `-l` in `addopts` prints fixture locals (logins) into CI logs: propose dropping it, not only `--no-showlocals`.
- `xdist_group` does nothing without `--dist loadgroup`; check each lane that runs `-n`.
- With docs, agents still wrote green-looking tests on a helper that failed silently: "prove setup" and the
  helper-diagnosis section are the rules that matter most; check them in every pilot.
- Never point a doc at a file that exists only in a worktree or experiment branch: grep the base branch first.
- Some agent harnesses filter or hide `git push` output; if you see none, re-run it unfiltered.
